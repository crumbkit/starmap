# Glossary

This page names each starmap concept once. Where a `starmap.toml` and the
Rust API spell a concept differently, the entry gives both spellings.

## name

A variable's name is the key of its table in `starmap.toml`, as in
`[variables.SHELF_PORT]`. A name starts with an ASCII letter or an
underscore and holds only ASCII letters, digits and underscores, so it
matches `[A-Za-z_][A-Za-z0-9_]*`. A name keeps the case it is written in,
which lets a file declare a variable that tools read in lower case, such as
`[variables.https_proxy]`. `HTTPS_PROXY` and `https_proxy` are two
variables, and a file may declare both. The parser refuses any other name
with `starmap::spec::bad_name`. The Rust API names it `starmap::Name`. A
family key and a group name have their own rules, which the `family` and
`group` entries give.

## type

The `type` field of a variable in `starmap.toml` states what the variable's
value is. The Rust API names it `starmap::Type`, and `Variable::value_type`
returns it.

The field takes one of the words `path`, `port`, `url`, `socket-address`,
`boolean` and `string`, or a table with one key:

- `{ path = { absolute = true } }` is a path that must be absolute. A
  relative path, including an empty one, then counts as unset.
- `{ integer = { min = 1, max = 100 } }` is a whole number from `min` to
  `max`, both included.
- `{ enumeration = ["dev", "prod"] }` is one of the listed values.
- `{ enumeration = "log-level" }` is one of the values of the named
  enumeration `log-level`, which the next entry describes.
- `{ url = { schemes = ["postgres", "postgresql"] } }` is a URL whose scheme
  is one of the listed schemes. Each scheme is written in lower case, and a
  value's scheme matches in any case. `{ url = {} }` means the same as
  `url`.
- `{ string = { pattern = "[0-9a-f]{40}" } }` is Unicode text that the
  pattern matches as a whole. `{ string = {} }` is the same type as the word
  `string`, which takes any Unicode text.
- `{ boolean = { true = ["1", "yes"], false = ["0", "no"] } }` is a boolean
  that takes only the listed spellings, which the paragraph on booleans
  below describes.

- `{ bytes = { encoding = "base64", length = 32 } }` is bytes written as
  text in an encoding, whose length after decoding is exactly `length`, or
  at least `min-length` when the table sets that key instead. A bytes table
  takes exactly one of the two lengths.

The word `boolean` reads the eight words `1`, `true`, `yes` and `on` as
true and `0`, `false`, `no` and `off` as false, in any mix of ASCII case,
and the value reaches the child process as `true` or `false`. A boolean
table declares its own spellings for an application that reads other
words. The table needs both a `true` list and a `false` list. A value
matches a spelling exactly, so `yes` in a list does not accept `YES`, and
the eight words are accepted only where a list holds them. The value
reaches the child process in the spelling it was set in, and a default is
one of the spellings. The parser refuses an empty list, an empty spelling
and a spelling listed twice, in one list or in both, with
`starmap::spec::empty_enumeration`. A value that is no listed spelling
fails with a text such as
`the value is not one of 1, yes for true and 0, no for false`. The Rust API
names the lists `starmap::Spellings`, holds them in `Type::Boolean`, and
holds a value read through them as `Value::Spelled`, which a `bool` field
reads.

A bytes type's `encoding` is `hex`, `base64` or `base64url`. `hex` takes two
digits per byte in upper or lower case. `base64` is RFC 4648 section 4 with
its padding required, and `base64url` is RFC 4648 section 5 with all its
padding or none, and partly padded text is refused. Each encoding refuses
whitespace. A length runs from 1 to 1024 bytes, and the parser refuses one
outside that range with `starmap::spec::bad_bytes`. A value that does not
decode fails with the text `the value is not base64`, and one of the wrong
size with `the value does not decode to 32 bytes` or
`the value does not decode to at least 16 bytes`. Neither text holds the
value or its decoded size. A shown value is held decoded, as `Value::Bytes`,
and is written back in its encoding's one spelling: lower case hex, padded
base64 or unpadded base64url. A shown value therefore reaches the child
process in that spelling, so a value written in upper case hex arrives in
lower case, and padded base64url arrives without its padding.

A generated variable may have a bytes type. Its first lookup creates as many
random bytes as the type's `length` gives, or its `min-length` when the type
sets a smallest length, and writes them in the declared encoding with that
same one spelling, so a generated value always passes its own check. The
type gives the length, so such a variable takes no `bytes` field, and the
parser refuses one beside the type with `starmap::spec::bad_bytes`. A
generated value takes 16 to 1024 bytes, so the parser also refuses a
generated bytes type whose length or `min-length` is under 16 with
`starmap::spec::bad_bytes`. A generated variable with the type `string`
takes its count from its `bytes` field, 32 without one, and is written as
unpadded base64url. A value the host already keeps is returned unchanged,
and the check after resolution refuses one whose encoding or length no
longer fits the type, naming the expected encoding and length; deleting the
kept value lets the host generate a new one. The Rust API names the rule `starmap::ByteRule`,
its encoding `starmap::Encoding`, its length `starmap::ByteLength` and the
count in a length `starmap::ByteCount`.

A pattern is written in the syntax of the Rust `regex` crate, which is close
to RE2's. It has no look-around and no backreferences, and matching takes
time linear in the value's length. A pattern that another implementation
must read should keep to the syntax that both the `regex` crate and RE2
accept. starmap anchors the pattern as `\A(?:pattern)\z`, so it matches the
whole value, and `^` and `$` are allowed and unnecessary. A pattern holds at
most 1024 bytes. The parser refuses a longer pattern, and one that the
`regex` crate does not compile within its default size limit, with
`starmap::spec::bad_pattern`, which quotes the pattern. A value that does not
match fails with the text `the value does not match the pattern <pattern>`,
which never holds the value. A refusal of a shown variable quotes the value
after that text, and a refusal of a withheld one never does, as the
`withheld` entry says. `starmap run` refuses such a value, and
`starmap explain` marks it invalid. A pattern that sets the `x` flag and ends
inside a `#` comment is refused, because the comment would hide the anchors;
ending the comment with a newline fixes it. The Rust API names the pattern
`starmap::Pattern`.

`Type::parse` reads a raw value in the type and returns a `Value`, nothing
when the value counts as unset, or a `TypeError` when the value does not fit
the type. `starmap explain` and
`starmap diff` print a variable's type under the name `type`.

## Unicode

A value that is not valid Unicode is refused with the text
`the value is not unicode text` by every type except `path`, which holds the
operating system's value as it is. A withheld variable always refuses such a
value. On Unix an environment value is bytes, and a value that is not UTF-8
is not Unicode. On Windows a value that holds an unpaired surrogate is not
Unicode.

Each place a value comes from follows the rule:

- The process environment is checked by each variable's type. A variable
  whose name is not Unicode is ignored, as an undeclared name is.
- A `.env` file must be UTF-8 as a whole, or `starmap run` refuses it as
  unreadable.
- `starmap run --set` takes only Unicode text, and refuses an argument that
  is not before it reads the spec.
- A value from a resolver or a provider is text, so it is always Unicode.
- A mode variable whose value is not Unicode leaves its local default to
  decide the mode, and the check then refuses the value.

Output that prints a value that is not Unicode replaces each invalid
sequence with U+FFFD. `starmap explain` prints a shown value that way, and
the refusal of a shown variable quotes it that way. A withheld value is
never printed or quoted. No test builds a value that is
not Unicode on Windows; the rule there follows from Rust's `OsStr::to_str`.

## enumeration

An enumeration type takes one of a fixed list of values. Each value is text
that is not empty and holds no whitespace. A variable writes the list inline,
as `type = { enumeration = ["dev", "prod"] }`, or names an enumeration that
the file declares, as `type = { enumeration = "log-level" }`. The Rust API
names the type `Type::Enumeration` and its values `starmap::Choices`.

A file declares a named enumeration in a top-level table, with each value as
a key and a description of that value as the key's value:

```toml
[enumerations.log-level]
debug = "Logs every request and its timing."
info = "Logs each request once."
warn = "Logs only failures and slow requests."
```

The values keep the file's order. A name starts with a lower case ASCII
letter and holds only lower case ASCII letters, digits and hyphens; the Rust
API names it `starmap::EnumerationName`. Every value has a description, which
follows the rules of `purpose`. The parser refuses a bad name, a value with
whitespace and an empty or non-text description with
`starmap::spec::bad_value`, a description of `?` with
`starmap::spec::guess`, and an empty table with
`starmap::spec::empty_enumeration`. A variable that names an enumeration the
file does not declare fails with `starmap::spec::enumeration_undeclared`.
Any number of variables may share one named enumeration, and a file may
declare one that no variable uses. An inline list has no descriptions.

A named enumeration follows every rule of an inline one: a default must be
one of its values, and a withheld variable cannot have it as its type. The
canonical form writes each `[enumerations.<name>]` table after `[mode]` and
before the variables, in name order, so renaming an enumeration or changing
a description changes the digest. `Spec::enumerations` lists the named
enumerations, `Choices::name` returns a named enumeration's name, and
`Choices::description` returns a value's description. `starmap explain`
prints the type as `log-level: one of debug, info, warn`, and its `--long`
column `values` lists each value with its description. `starmap diff`
reports a changed description as a change of `values`.

## withheld

Withheld is how a variable's value is shown. A variable states it with
`show = "withheld"`, and the Rust API spells it `Show::Withheld`. The other
word is `shown`, which is `Show::Shown`.

A withheld value is held in a `starmap::Secret`, whose `Debug` prints
`Secret(••••••••)` whatever the value. `starmap explain` prints eight dots
in place of a withheld value and gives it no text in JSON. A withheld
variable has no default, because a default would sit in `starmap.toml` in
plain text, and its type is `string`, with or without a pattern, or
`bytes`. A check reports a withheld value that does not match its pattern by
naming the pattern alone, and one that does not decode or has the wrong size
by naming the encoding or the length alone. A check holds the bytes that a
withheld bytes value decodes to in a `starmap::SecretBytes`, whose memory is
zeroed when it is dropped, beside its text, and `Environment::apply` gives a
child the text. A refusal of a shown variable's value quotes the value after
its reason, as in `SHELF_PORT: the value is not a port from 1 to 65535 (the
value is "80a")`, and a refusal of a withheld variable's value never quotes
it. The quote holds the first 64 characters of the value and then `…` when
the value is longer, and it is written as a JSON string, so a quote, a
backslash or a newline in the value is escaped. The parser refuses a withheld
variable that breaks either rule.

The parser also forces `show = "withheld"` on every variable whose source is
`secret` or `generated`, and it refuses `show = "shown"` on them. A variable
with any other source, which is `setting`, `inherited` or `provided`, can be
withheld too. Such a variable gets its value as any other variable of its
source does: from the shell, from `.env` beside the spec or from `--set`, from
its path when a `setting` has a `bind`, or from a provider. Starmap does not
ask for it at a terminal. Only a `secret` with no `bind` is asked for there.
A withheld variable is kept out of output although it is not a secret in the
sense of the next entry.

## secret

Secret names a source: `source = "secret"` in `starmap.toml`, and
`Source::Secret` in the Rust API. A `secret` variable is always withheld. Its
optional `bind` is a `one-password` reference that a resolver reads the value
from, with an optional `cache = false` that keeps the value out of any cache
of resolved values.

A secret differs from a withheld `setting`. The word `secret` says where the
value comes from, and `withheld` says only how the value is shown. A
`setting` takes only a `path` bind, which is a template that a host expands
into the value.

`starmap::Secret` is the Rust type that holds any withheld value, whichever
source the value comes from.

## provided

Provided has two spellings in a `starmap.toml`, and they sit in different
places.

- The source is the word `provided` in a variable's `source` field:
  `source = "provided"`. The Rust API spells it `Source::Provided`.
- The bind key is `provided` inside the variable's `bind` table, as in
  `bind = { provided = "multiverse/port", process = "api" }`. Its value is a
  provider kind written `<host>/<kind>`, and the other keys of the table are
  qualifiers that tell the provider which value to supply. The Rust API spells
  the whole bind `ProvidedRef`, and the kind `ProviderKind`.

A source of `provided` needs a bind with the `provided` key, and a bind with
the `provided` key is allowed only on a source of `provided`. A spec that
pairs them any other way fails with `starmap::spec::bind_mismatch`. To tell
the two apart, look at the key: the source is the value of `source`, and the
bind key is a key inside `bind`.

## Unset, UnsetRule and the unset field

The `unset` field of a variable in `starmap.toml` says what happens when the
variable has no value. It is one of the words `required` and `optional`, or
a table that has either `local` (one of those words) or `default` (text
that the variable's type reads), and an optional `production` (one of those
words).

`Unset` is the Rust enum for the rule in one mode, with the variants
`Required`, `Optional` and `Default(Value)`.

`UnsetRule` holds an `Unset` for local mode and one for production mode.
`UnsetRule::in_mode` returns the rule of a mode, and `Variable::unset`
returns a variable's `UnsetRule`. When the file states no `production`, the
production rule equals the local one. A stated `production` is `required`
or `optional`, because a production rule takes no default of its own.

An empty value counts as unset, wherever it comes from: the process
environment, `.env`, `--set`, a provider or a resolver. So `FOO=` gives a
variable its default, leaves an optional variable unset, and leaves a
required variable missing. An empty value in a later layer does not hide a
value from an earlier one, so `FOO=` in the shell leaves the value that
`.env` gives `FOO` in place. `starmap::capture` binds nothing for an empty
value, and `check` treats an empty bound value as unset before any type
reads it.

## effect

The optional `effect` field of a variable in `starmap.toml` is one sentence
that says what the application does when the variable is unset, such as
`effect = "Calls are not recorded."`. Any variable may have one. Its text
follows the rules of `purpose`: the parser refuses an empty or blank
sentence with `starmap::spec::bad_value`, and `?` with
`starmap::spec::guess`. `starmap init` does not write it.
`Variable::effect` returns the sentence, or nothing when the file states
none.

The effect counts toward the canonical form and the digest, as the purpose
does. The canonical form writes it right after `purpose`, and only when the
variable has one, so a file without effects keeps its digest.
`starmap explain --long` prints it in the `effect` column after `purpose`,
and `starmap explain --json` leaves the field out when the variable has
none. `starmap diff` reports an effect that was added, changed or removed
as a change of the field `effect`.

## check

A check is a rule of the application that its own code decides, such as a
port above 1024. A field of a struct that derives `Env` names its check
function with `#[starmap("SHELF_PORT", check = unprivileged)]`. The
function takes a reference to the field's type without its `Option`. A
shown field's check returns `Result<(), String>`, and a withheld field's
check returns `Result<(), &'static str>`, so the reason it gives cannot
hold the secret. A function of another signature fails to compile.

`Env::from_vars` runs each check inside the same pass as the built-in
checks, on every variable that holds a value after its type and its unset
rule pass, a default included. A variable that stays unset, or whose value
its type refuses, is not passed to its check. A refused value is the
finding `Problem::Rejected` with the check's reason, among the other
findings in the spec's order, and is written as `SHELF_PORT: the port must
be above 1024`. A shown variable's value is quoted after the reason, as an
invalid value is, and a withheld variable's value never is.

The optional `check` field of a variable in `starmap.toml` is one sentence
that states the check for a reader, such as
`check = "The port must be above 1024."`. starmap never runs it, and other
implementations only display it. Its text follows the rules of `purpose`.
It counts toward the canonical form and the digest, as the effect does: the
canonical form writes it right after `effect`, and only when the variable
has one, so a file without check sentences keeps its digest.
`starmap explain --long` prints it in the `check` column, `starmap explain
--json` leaves the field out when the variable has none, and `starmap diff`
reports a change of the field `check`.

`starmap check` notes a field whose attribute names a check for a variable
without a check sentence, and a check sentence whose variable no field in
src checks. Each is a note on standard error and a list in the JSON
document, and neither fails the command.

## flag override

A flag override is a command-line flag that replaces a variable's value for
one run. The application reads the variable only through its struct that
derives `Env`, and the flag wins when it is given. starmap has no function
for this, because the methods of `Option` cover every shown single variable.
A withheld variable should not get a flag override, because a secret on a
command line shows in the process list, and a family should not get one,
because it has no single flag:

| The field | The flag | The value the application uses |
| --- | --- | --- |
| `port: Port`, a required variable or one with a default | `Option<Port>` | `cli.port.unwrap_or(env.port)` |
| `catalogue: Option<Url>`, an optional variable | `Option<Url>` | `cli.catalogue.or(env.catalogue)` |
| `debug: bool` | a switch, `bool` | `cli.debug \|\| env.debug` |

The expression `cli.debug || env.debug` can turn the switch on but never off,
and `.or` can never clear an optional value. A flag that must be able to turn
a switch off is an `Option<bool>` with clap's `ArgAction::Set`.

`Env::load` refuses a required variable that is unset before the
application looks at any flag. A variable that is required only when its
flag is not given is therefore declared `unset = "optional"`, and the
application reports the missing value itself, as in
`cli.port.or(env.port).ok_or("pass --port or set SHELF_PORT")?`.

The field becomes an `Option<Port>`. `Env::load` and `starmap run` then
accept a missing SHELF_PORT, and `starmap explain` lists it as optional, so a
deployment that sets neither the flag nor the variable fails only at the
application's own `ok_or`. The variable's purpose text should name the flag.

The flag's value does not pass through the variable's declared type or its
field's check. Giving the flag the field's type, such as `starmap::Port`,
makes clap refuse what that type's `FromStr` refuses. The spec's further
rules, such as the allowed schemes of a URL or the range of an integer, and
the field's check do not apply to the flag's value.

A flag override replaces clap's `env` argument, as in
`#[arg(env = "SHELF_PORT")]`, which reads the variable outside the struct.
clap's help then no longer names the variable, so name it in the flag's help
text.

## family

A family is a set of variables whose names are chosen at run time, such as
one database url per region. A file declares one as a top-level
`[families.<PREFIX>]` table that takes the fields of a variable table, and
every member shares them:

```toml
[families.SHELF_DB_URL]
purpose = "The database of one region, keyed by the region's code."
type = "url"
unset = "optional"
show = "shown"
source = "setting"
```

A member is a variable whose name is the prefix, an underscore and a key,
such as `SHELF_DB_URL_EU` with the key `EU`. The prefix follows the rule of
a variable name. A key starts with an upper case ASCII letter or a digit
and holds only upper case ASCII letters, digits and underscores, and a
member's whole name has at most 128 bytes. A family's keys are open, so any
key is a member, unless the file lists them with `keys = ["ACME",
"GLOBEX"]`. A listed family's members are exactly its keys, and a value
whose key it does not list is the finding `Problem::UnlistedKey`, which
`starmap run` reports with the code `starmap::family::unlisted_key`. A
listed key that breaks the key rule fails with `starmap::spec::bad_value`.

No family has a default, because a default would apply to keys that nobody
names. An open family is optional in every mode, because starmap cannot
know which keys it must have. A listed family may be required, in every
mode or per mode, and each listed key whose member is unset is then
`Problem::Missing`, which names the member. A family's source is a setting
without a bind, or inherited, because a secret, generated, provided or
bound variable needs one bind per member. A family may be withheld, with
the type string.

`starmap::spec::bad_family` refuses a default, a required open family, an
empty, repeated or overlong key list, a refused source, a declared variable
that is a member of a family, and two families whose prefixes would share a
member, such as `SHELF_DB` and `SHELF_DB_URL`. The prefix test ignores
listed keys, so each name has one declaration however the keys change. A
group may not name a family's prefix or member.

`capture`, `.env` and `--set` take every member's value, and `check` checks
each in the family's type after the declared variables, in name order. A
finding names the member. `starmap check` counts a read of a member's name
as declared, unless its key is one that a listed family does not list.
Families count toward the canonical form and the digest, which writes each
family after the groups and before the variables, in prefix order, with
its listed keys last and in key order, so reordering the keys keeps the
digest. The Rust API names a family's declaration
`starmap::FamilyDeclaration`, and `Spec::families`, `Spec::family` and
`Spec::declared` read it. A struct field reads a family with
`#[starmap(family = "SHELF_DB_URL")]` into a `starmap::Family<T>`, which
holds each set member's value under its key, in key order.

## group

A group is a set of variables that must be set together or not at all,
such as the account, key and secret of one external service. A file
declares one as a top-level table with one field, `variables`:

```toml
[groups.mirror]
variables = ["SHELF_MIRROR_ACCOUNT", "SHELF_MIRROR_KEY", "SHELF_MIRROR_SECRET"]
```

A group name starts with a lower case ASCII letter and holds only lower
case ASCII letters, digits and hyphens, as an enumeration name does, and a
bad name fails with `starmap::spec::bad_value`. A member that the file does
not declare fails with `starmap::spec::group_undeclared`, which names the
group and the variable. `starmap::spec::bad_group` refuses a group with
fewer than two members or a repeated member, a variable in two groups, and
a member with a default or a generated value, because a default or a
generated value always counts as set. It also refuses a group that names
the prefix of a family or a member of one, because families cannot join
groups, and it checks this before it checks that the member is declared.
The Rust API names a group
`starmap::Group` and its name `starmap::GroupName`. `Spec::groups` lists
the groups in name order, `Spec::group` returns one by name, and
`Spec::group_of` returns the group a variable belongs to.

`check` applies the rule after it has read each variable. A member counts
as set when the check holds a value for it, so `FOO=` counts as unset. When
at least one member is set and another is unset, each unset member that
has no finding of its own gets `Problem::GroupIncomplete`, which names the
group and the members that are set. A member that is missing because it is
required gets only that finding. A group that is wholly unset or wholly
set passes. A member may be required in production and optional locally;
the group is then required in production and all or none locally.
`starmap run` reports the finding with the code `starmap::group::incomplete`,
and `#[derive(Env)]` refuses the read with the same text.

Groups count toward the canonical form and the digest, because a group
changes what `check` accepts. The canonical form writes each group after
the named enumerations and before the variables, in name order, with its
members in the file's order. A file without groups keeps its digest.
`starmap explain --long` prints the variable's group in the `group`
column, and `starmap explain --json` leaves the field out for a variable
without one. `starmap diff` reports a variable that joins, leaves or
changes group as a change of the field `group`.

## built-in variable

A built-in variable is a variable that `starmap run --only-declared` passes
from the shell to the program without a declaration, because the operating
system and common tools need it. The list is fixed in starmap, one list per
platform, and no `starmap.toml` adds to it. The Rust API names a
platform's list `starmap::BuiltIns`, with `BuiltIns::UNIX`,
`BuiltIns::WINDOWS` and `BuiltIns::current`, the list of the platform that
starmap is built for.

On Unix systems, macOS and Linux among them, the built-in variables are:

| Name | Why it passes |
| --- | --- |
| `PATH` | The program and every program it starts are found on it. |
| `HOME` | Tools find their configuration and caches under the home directory. |
| `USER` | Tools read the name of the person who runs them from it. |
| `LOGNAME` | POSIX names it as the login name, and some tools read it where others read `USER`. |
| `SHELL` | Tools that start a shell for the person start the one it names. |
| `TMPDIR` | Temporary files go to the directory it names, which macOS sets per user. |
| `LANG` | It sets the locale, which decides the character encoding and the language of messages. |
| `LC_ALL`, `LC_COLLATE`, `LC_CTYPE`, `LC_MESSAGES`, `LC_MONETARY`, `LC_NUMERIC`, `LC_TIME` | Each is a locale category of POSIX, which sets one part of the locale and overrides `LANG`. |
| `LC_ADDRESS`, `LC_IDENTIFICATION`, `LC_MEASUREMENT`, `LC_NAME`, `LC_PAPER`, `LC_TELEPHONE` | Each is a locale category that glibc adds. |
| `TERM` | The program holds the terminal, and it names the terminal's kind and what it can draw. |
| `TZ` | The C library reads the time zone from it, so local times stay the same. |

Any other name that starts with `LC_`, such as `LC_TERMINAL`, is not built
in.

On Windows, where a name matches in any ASCII case, they are:

| Name | Why it passes |
| --- | --- |
| `PATH` | The program and every program it starts are found on it. |
| `PATHEXT` | It lists the file extensions that a program name may leave out, such as `.EXE`. |
| `SystemRoot` | Windows libraries, networking among them, fail to load without the Windows directory. |
| `SystemDrive` | Tools build the paths of system directories from the drive that holds Windows. |
| `windir` | Older programs read the Windows directory from it where newer ones read `SystemRoot`. |
| `ComSpec` | A program that runs a shell command starts the command interpreter it names. |
| `TEMP` | Temporary files go to the directory it names. |
| `TMP` | Windows reads it before `TEMP` when it chooses the directory of temporary files. |
| `USERPROFILE` | It names the home directory, where tools find their configuration. |
| `USERNAME` | Tools read the name of the person who runs them from it. |
| `APPDATA` | Tools keep each person's roaming configuration under the directory it names. |
| `LOCALAPPDATA` | Tools keep each person's caches and local data under the directory it names. |

The Windows list is not tested against a real child process, because the
project's CI runs its tests on Linux and macOS only. A program on Windows
may need a variable that the list leaves out, such as `ProgramFiles`, and
the application then declares it with `source = "inherited"`.

`starmap run --only-declared -- <program>` starts the program with an
environment of only declared variables: each declared variable that has a
value, each member of a declared family that is set, and each built-in
variable that the shell sets. The program inherits nothing else, so a read
of an undeclared variable finds it unset, and a test that depends on that
variable fails. Code that falls back to a default for an unset variable
still passes, so `starmap check` is the command that finds the undeclared
variables that `src` reads. An application that needs another variable of
the shell, such as `SSH_AUTH_SOCK`, declares it with
`source = "inherited"`. A file may declare a built-in name to give it a
type, and the program then receives the checked value, or no value when the
check leaves the variable unset. `starmap run` adds `TRACEPARENT` and
`TRACESTATE` when its usage log records the run, as it does without the
flag. The flag is off by default, and `starmap run` without it lets the
program inherit every variable of the shell. `starmap explain` without a
name lists the built-in variables of its platform in its note. In the Rust
API, `Environment::apply_only_declared` builds the same environment on a
`Command` from the variables and the list that the caller passes.

## pointer

A pointer is a `starmap.toml` that names the file that declares the
variables, in place of declaring them itself. A file is a pointer when its
top level has the key `spec`. The Rust API names it `starmap::Pointer`, and
`Pointer::parse` returns it, or nothing for a file without `spec`.

```toml
spec = "config/environment.toml"
src = ["src"]
dotenv = ".env"
```

Each path is relative to the directory of the pointer file. `spec` is the
declaration file. `src` lists the directories whose source `starmap init`
and `starmap check` scan, is `["src"]` when the pointer leaves it out, and
scans nothing when it is an empty list.
`dotenv` is the file that `starmap run` reads values from, and is `.env`
when the pointer leaves it out. `starmap init`, `check`, `explain`, `diff`
and `run` follow a pointer as if `--spec` named the declaration file, and
`#[derive(Env)]` embeds the declaration file and names it in
`Env::SPEC_FILE`. `starmap run` keeps the pointer's directory as the
checkout.

A file either points or declares. A pointer that also has `variables`,
`groups` or `mode` fails with `starmap::spec::pointer_declares`. A pointer reached where
a declaration file belongs, such as the file that another pointer names,
fails with `starmap::spec::pointer_chain`, so starmap follows at most one
pointer. A pointer has no digest of its own, and `starmap check` prints the
digest of the declaration file.

## Clippy entries

The Clippy entries are four `disallowed-methods` entries in an
application's `clippy.toml`, one for each of `std::env::var`,
`std::env::var_os`, `std::env::vars` and `std::env::vars_os`. With them,
Clippy refuses a call of those methods in the application's own code, so
the code reads the environment only through the struct that derives `Env`.
The derive's generated `Env::load` carries the `#[expect]` that lets it
make the one read.

```toml
disallowed-methods = [
    { path = "std::env::var", reason = "read the environment through the struct that derives starmap::Env, whose variables starmap.toml declares" },
]
```

Clippy applies the entries to every target of the crate, so it also
reports a read in a build script or a test, which starmap's scan skips. A
read there, such as `OUT_DIR` in `build.rs`, takes
`#[expect(clippy::disallowed_methods, reason = "...")]`.

starmap requires the entries for the crate of each `.rs` file that its scan
reads. The crate's directory is the nearest directory above the file that
holds a `Cargo.toml`, however far above, so `src = ["."]` and
`src = ["crates"]` reach the crate of each file. A file with no
`Cargo.toml` above it belongs to the spec's directory. The file that holds the entries is the one that Clippy
reads for the crate: `.clippy.toml` or `clippy.toml` in the crate's
directory, or else in the nearest directory above it that has one. Clippy
reads that one file and merges no other, so a crate with a `clippy.toml` of
its own needs the entries there. Clippy skips a directory that has one of
those names, and starmap does too. starmap does not read
`CLIPPY_CONF_DIR`, so an application that sets it keeps the entries in the
file that this search finds as well.

The search for a `clippy.toml` stops at the repository's root, which is
the nearest directory at or above the crate's directory that holds `.git`.
Without a repository, the search stops at the root of the crate's Cargo
workspace, which is the nearest directory at or above the crate's
directory whose `Cargo.toml` has a `[workspace]` table. Without a
workspace either, starmap reads only the crate's directory. starmap never
reads or edits a `clippy.toml` above the directory where the search stops,
although Clippy does read one there. The `clippy.toml` that init writes is
nearer to the crate, so Clippy then reads it in place of the file above,
and a setting that only the file above holds no longer applies to the
crate.

`starmap init` adds each missing entry after the entries that a file
lists, and keeps the file's other entries, comments, layout and mode. It
writes through a symbolic link to the file that the link names, and its
messages name that file. When no directory has a file, init writes
`clippy.toml` beside the spec when the spec's directory is the crate's
directory, or a directory above it where the search reaches, and in the
crate's directory otherwise. `starmap init --clippy`
adds only these entries and leaves the spec alone, for an application whose
spec exists. It lists no variable, and says what it did to each file in
the note of its output. An entry counts as
present when it is a string that holds the method's path or a table whose
`path` holds it, in an array or in `[[disallowed-methods]]` tables,
whatever its reason.

`starmap check` fails with `starmap::clippy::unbanned` for each file that
lacks an entry. A `clippy.toml` that cannot be read, is over 256 KiB, is
not UTF-8 text or valid TOML, or whose `disallowed-methods` is not an
array, fails both commands with `starmap::clippy::invalid`, and neither
command rewrites it. A symbolic link that leads to no file, or back to
itself, cannot be read. When the scan reads no `.rs` file, as in an
application written in another language, check requires no entries and
init writes no `clippy.toml`.

## tool table

A tool table is a `[tool.<name>]` table, where a tool such as a generator,
a linter or a host keeps settings of its own in the file that starmap reads.
A file that declares variables may hold tool tables at its top level and in
each variable, as `[tool.codegen]` and `[variables.SHELF_PORT.tool.codegen]`,
and a pointer may hold them at its top level. The Rust API names one
`starmap::ToolTable`, which holds its keys and values as the text of a TOML
document. `Spec::tool`, `Variable::tool` and `Pointer::tool` return the
table of one tool, and `tools` lists them in name order.

starmap checks only that `tool` is a table whose values are tables, and
refuses any other value with `starmap::spec::bad_value`. It never reads the
keys inside a tool table. The canonical form and the digest leave tool
tables out, so an edit to a tool table never changes a file's digest, and
`starmap explain`, `check`, `diff` and `init` print the same output for a
file with tool tables as for the same file without them. starmap never
merges a pointer's tool tables into those of the file it names.
